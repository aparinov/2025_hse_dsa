#### **Часть 2: Мое предварительное видение архитектуры и стека (Strawman Proposal)**

Исходя из цели "быстрый MVP" и состава команды, я предлагаю следующую архитектуру и стек. Это "соломенное чучело" – предложение, которое мы можем обсуждать и менять после ваших уточнений.

**Архитектура: "Величественный Монолит" (Majestic Monolith)**

Никаких микросервисов. Единое веб-приложение, которое содержит в себе всю логику.
*   **Плюсы:** Простота разработки и развертывания, одна кодовая база, одна база данных, нет сетевых задержек между сервисами. Идеально для команды из 2 человек.

**Предлагаемый стек:**

1.  **Backend Framework: Django**
    *   **Почему?** "Батарейки в комплекте" (Batteries included). Мы получаем из коробки:
        *   **Мощную ORM:** для работы с Postgres.
        *   **Готовую админ-панель:** для управления данными (пользователи, проекты, теги) без написания кода. Это киллер-фича для MVP.
        *   **Систему аутентификации:** которую легко расширить.
        *   **Шаблонизатор (Django Templates):** для быстрой отрисовки страниц на сервере.
    *   *Альтернатива: FastAPI. Он быстрее, но требует больше "обвязки" для ORM, админки, структуры проекта. Для MVP Django даст нам больший буст скорости разработки.*

2.  **Frontend: HTML + CSS + щепотка JavaScript (Server-Side Rendering)**
    *   **Почему?** Мы не создаем отдельный SPA (Single-Page Application). Вместо этого Django будет сам генерировать HTML-страницы.
    *   **Плюсы:**
        *   Команде не нужно глубоко погружаться во Frontend-фреймворки (React/Vue).
        *   Супер быстрая разработка.
        *   Берем готовый CSS-фреймворк (например, **Bootstrap** или **Tailwind CSS**), чтобы все выглядело прилично без дизайнера.
        *   Интерактивность (например, подача заявки без перезагрузки страницы) можно легко добавить с помощью **HTMX** или небольшого количества нативного JS/jQuery.
    *   *Это самый прямой путь к MVP. Отдельный клиент на Flutter/React – это усложнение на порядок.*

3.  **База данных: PostgreSQL**
    *   **Почему?** Надежная, мощная, отлично поддерживается Django. Имеет встроенные возможности для полнотекстового поиска (**pg_trgm**, **tsvector**), которых с головой хватит для MVP.
    *   **Про Neo4j:** Это графовая база данных, идеальная для сложных рекомендательных систем ("найти проекты, в которых участвовали коллеги людей, с которыми ты работал..."). Для MVP это **однозначный оверкилл**. Мы можем реализовать простые рекомендации на тегах в самом Postgres. Давайте отложим Neo4j в бэклог на будущее.

4.  **Поиск: Встроенный Full-Text Search в PostgreSQL**
    *   **Почему?** Не требует развертывания и поддержки отдельного сервиса (как Elasticsearch). Для нашего объема данных и требований к MVP его будет более чем достаточно. Интегрируется с Django через `django.contrib.postgres`.

5.  **Развертывание (DevOps): Docker + Docker Compose**
    *   **Почему?** Упаковываем наше Django-приложение и Postgres в контейнеры. Это позволяет любому разработчику (и серверу) запустить проект одной командой.
    *   **Хостинг:** Любой простой VPS (DigitalOcean, Vscale, Яндекс.Облако), где мы поднимем Docker.

#### **Итоговая концепция MVP:**

*   **Одно веб-приложение на Django.**
*   **Единый интерфейс для всех:** Логика и внешний вид меняются в зависимости от роли пользователя (студент/преподаватель), который залогинен.
*   **Простая регистрация:** Логин/пароль. Интеграцию с SSO университета держим в уме, но не делаем.
*   **Профили:** Студент заполняет профиль и выбирает интересы из заданного списка тегов.
*   **Проекты:** Преподаватель создает проекты, указывает теги.

*   **Рекомендации:** На отдельной странице или в блоке "Вам может быть интересно" показываем проекты, у которых максимальное пересечение тегов с профилем студента.

#### 1. Архитектурная Схема (High-Level)

Мы строим классическое монолитное веб-приложение. Просто, надежно, идеально для MVP.

```
+----------------+      +---------------------+      +------------------------+      +----------------+
|                |      |                     |      |                        |      |                |
|  Пользователь  | <--> |   Веб-сервер (Nginx)| <--> |  Приложение (Gunicorn) | <--> |    База данных |
| (Браузер)      |      | - раздача статики   |      |   + Django App         |      |   (PostgreSQL) |
|                |      | - proxy             |      |   - Бизнес-логика      |      |                |
+----------------+      +---------------------+      |   - Рендеринг HTML     |      +----------------+
                                                     +------------------------+
```

*   **Nginx:** Будет выступать в роли reverse-proxy, принимать запросы от пользователей и передавать их нашему Django-приложению. Также он будет эффективно раздавать статические файлы (CSS, JS, картинки).
*   **Gunicorn:** WSGI-сервер, который будет запускать несколько процессов нашего Python/Django приложения, обеспечивая параллельную обработку запросов.
*   **Django App:** Сердце системы. Здесь вся наша логика: модели, контроллеры (views), шаблоны (templates).
*   **PostgreSQL:** Наша основная и единственная база данных. Будет хранить всё: пользователей, проекты, теги, заявки.

    class Status(models.TextChoices):
        PENDING = 'PENDING', 'На рассмотрении'
        APPROVED = 'APPROVED', 'Принята'
        REJECTED = 'REJECTED', 'Отклонена'

    project = models.ForeignKey(Project, on_delete=models.CASCADE, related_name="applications", verbose_name="Проект")
    student = models.ForeignKey(User, on_delete=models.CASCADE, related_name="applications", verbose_name="Студент")
    status = models.CharField(max_length=10, choices=Status.choices, default=Status.PENDING, verbose_name="Статус заявки")
    
    created_at = models.DateTimeField(auto_now_add=True)
    
    class Meta:
        # Студент может подать только одну заявку на проект
        unique_together = ('project', 'student')

#### 3. Реализация Ключевых Бизнес-процессов

1.  **Авторизация и Роли:**
    *   При регистрации (для MVP) добавляем поле "Роль" (Студент/Преподаватель). Изначально можем всех делать студентами и менять роль вручную через админку.
    *   В Django используем декораторы или mixins для ограничения доступа. Например, `CreateProjectView` будет доступна только для пользователей с `user.role == 'TEACHER'`.

2.  **Поиск и Рекомендации:**
    *   **Поиск:** Используем `django.contrib.postgres.search`. Создаем `SearchVector` по полям `title` и `description` в модели `Project`. Это дает нам полнотекстовый поиск "из коробки".
    *   **Фильтрация:** Через GET-параметры в URL (`/projects/?tag=python&tag=ml`). Библиотека `django-filter` упростит эту задачу.
    *   **Рекомендации (MVP):**
        *   Получаем теги текущего студента: `user_tags = user.interests.all()`
        *   Ищем проекты, которые еще не в архиве и на которые студент не подавал заявку.
        *   Аннотируем (добавляем) к каждому проекту количество совпадений по тегам: `Project.objects.annotate(tag_match=Count('tags', filter=Q(tags__in=user_tags)))`
        *   Сортируем по убыванию `tag_match` и отдаем топ-5. Этот запрос достаточно быстрый для тысяч проектов.

3.  **Подача и Рассмотрение Заявки:**
    *   **Студент:** На странице проекта видит кнопку "Подать заявку". Нажатие создает объект `Application` со статусом `PENDING`.
    *   **Преподаватель:** На странице своего проекта видит список заявок. У каждой заявки есть кнопки "Принять" и "Отклонить".
    *   **Логика при принятии заявки:**
        1.  Статус `Application` меняется на `APPROVED`.
        2.  Студент добавляется в `project.participants`.
        3.  Проверяем, не заполнились ли все места в проекте. Если `project.participants.count() >= project.max_participants`, то статус проекта меняется на `IN_PROGRESS`.
    *   Можно настроить отправку email-уведомлений студенту об изменении статуса его заявки.

#### DBeaver: Инструкция для Далее

##### Зачем он нужен?

DBeaver — это твой визуальный "проводник" в базу данных. Вместо команд в чёрном терминале ты получаешь удобный интерфейс, чтобы:

*   **Смотреть:** Визуально видеть все таблицы, их структуру и данные внутри.
*   **Проверять:** Убедиться, что твои Django-миграции (`migrate`) создали правильные колонки в таблицах.
*   **Отлаживать:** Вручную менять данные для теста (например, поменять статус проекта и посмотреть, как отреагирует сайт).
*   **Анализировать:** Быстро писать и выполнять SQL-запросы, чтобы найти нужную информацию, не запуская Django-приложение.

##### В какой момент его использовать?

**1. Сразу после первого запуска проекта.**
*   Ты запускаешь проект командой `docker-compose up`.
*   Открываешь DBeaver и создаешь новое подключение к PostgreSQL.
*   **Параметры подключения:** берешь из своего файла `docker-compose.yml` (host: `localhost`, port: `5432`, database, user, password).
*   **Цель:** Убедиться, что база данных поднялась и ты можешь к ней подключиться.

**2. В процессе разработки (постоянно).**
Ты начинаешь его использовать каждый раз, когда:
*   Создал модели и применил миграции (чтобы проверить, что таблицы `users_user`, `projects_project` и другие появились).
*   Нужно посмотреть, какие данные сохранились в базе после того, как ты заполнил форму на сайте.
*   На сайте возникает ошибка, и ты подозреваешь, что проблема в данных.
*   Нужно быстро что-то поправить в базе руками для теста, не создавая для этого отдельную фичу.
